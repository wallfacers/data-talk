# Internationalization (i18n) Guide

Full-stack i18n is already in place: custom lightweight solution on the frontend, Spring `MessageSource` on the backend. Supported languages: `zh-CN` (default) and `en-US`.

## Frontend

### Architecture

| Layer | Location | Purpose |
|-------|----------|---------|
| Dictionary | `client/src/i18n/messages.ts` | `zh-CN` / `en-US` key-value maps, supports `{name}` interpolation |
| Provider | `client/src/i18n/provider.tsx` | `I18nProvider` React Context, exposes `{ language, setLanguage, t }` |
| Hook | `client/src/i18n/use-i18n.ts` | `useI18n()` returns `{ language, setLanguage, t }` |
| Persistence | `client/src/stores/ui-settings-store.ts` | Zustand store with `localStorage`, detects `navigator.language` on first load |
| HTTP header | `client/src/services/http.ts` | `beforeRequest` hook sets `Accept-Language` from current language state |

### Usage

```tsx
import { useI18n } from "@/hooks/use-i18n";

function MyComponent() {
  const { t } = useI18n();
  return <Button>{t("common.save")}</Button>;
}
```

**With interpolation**:

```tsx
t("session.switch.success", { name: currentSession?.title ?? "" })
// messages.ts value: "已切换到 {name}" / "Switched to {name}"
```

### Adding New Translation Keys

1. Add the key to **both** `zh-CN` and `en-US` objects in `messages.ts`
2. Keys use dot-notation grouping: `common.*`, `session.*`, `settings.*`, `workspace.*`, `connection.*`, `chat.*`, `dataGrid.*`, `channel.*`, `theme.*`, `stage.*`, `action.*`
3. Use `{paramName}` for interpolation — the engine replaces via regex `/\{(\w+)\}/g`

### Rules

- **No hardcoded user-facing strings** in JSX/TSX. All visible text (buttons, titles, toasts, placeholders, error messages, empty states) must go through `t()`
- Code comments may remain in Chinese — they are not user-facing
- Language switcher lives in the Settings page (`client/src/pages/settings.tsx`)

## Backend

### Architecture

| Component | Location | Purpose |
|-----------|----------|---------|
| Config | `server/data-talk-adapter/.../config/I18nConfig.java` | `ResourceBundleMessageSource` (basename: "messages"), `AcceptHeaderLocaleResolver` (default `zh_CN`) |
| Bundle (EN) | `server/data-talk-adapter/.../resources/messages.properties` | Default English messages, 35+ keys |
| Bundle (ZH) | `server/data-talk-adapter/.../resources/messages_zh_CN.properties` | Simplified Chinese messages, mirror keys |
| Translator | `server/data-talk-application/.../i18n/Translator.java` | Spring component wrapping `MessageSource`, provides `get(code, args...)` and `getOrDefault(code, fallback, args...)` |

### Usage

```java
@Service
public class MyService {
    private final Translator translator;

    public String buildMessage() {
        return translator.get("error.session.notFound", sessionId);
    }
}
```

Backend uses Java `MessageFormat` placeholders: `{0}`, `{1}`, etc.

### Adding New Translation Keys

1. Add the key to **both** `messages.properties` and `messages_zh_CN.properties`
2. Keys follow convention: `error.*`, `success.*`, `label.*`, `tooltip.*`
3. Keys in the two files must stay in sync — missing keys in one locale fall back to default bundle silently

### Rules

- All user-facing error messages, success toasts, connection test results, and default titles must go through `Translator`
- `Accept-Language` header from frontend requests is automatically resolved by `AcceptHeaderLocaleResolver`
- Historical/existing data does not require localization

## End-to-End Flow

```
User switches language in Settings
  → Zustand persists to localStorage
  → I18nProvider updates context + document.documentElement.lang
  → Next HTTP requests carry updated Accept-Language header
  → Backend resolves locale and returns localized error/success messages
```

## Testing

- Manually toggle language in Settings and verify all UI text switches
- Verify backend error messages respect the `Accept-Language` header (test via API client)
- Ensure no new hardcoded strings slip in during code review
