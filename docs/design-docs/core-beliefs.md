# 核心理念

DataTalk 项目遵循以下操作原则。这些理念指导架构决策和日常开发。

## 1. 仓库即记录系统

所有知识必须存在于仓库本地的版本化工件中（代码、Markdown、Schema、执行计划）。存在于聊天记录、Google Docs 或人脑中的知识，对智能体来说不存在。

## 2. 地图优于手册

上下文是稀缺资源。文档结构应实现渐进式披露：从一个小而稳定的切入点（CLAUDE.md）开始，指向更深层的真实信息来源。避免将所有内容塞入一个巨大文件。

## 3. Action 即能力边界

所有面向 AI 暴露的能力统一通过 Action Registry 注册。新增一个能力 = 新建一个 `@DataTalkAction` Handler，零核心代码改动。不允许绕过 Registry 的后门能力。

## 4. 领域纯净性

`domain` 模块不依赖任何框架（Spring、Jackson 注解用于序列化除外）。领域逻辑通过接口契约与外部世界解耦。sealed interface 保证编译期类型安全。

## 5. 事件驱动优先

所有状态变更通过 `DtEvent` 事件流传播。SessionBus 是唯一的事件分发通道。客户端通过 SSE 订阅事件流，服务端持久化事件以支持回放和断线恢复。

## 6. AI 即推理层，后端即执行层

OpenCode 作为纯推理服务，不直接访问数据库或文件系统。所有副作用操作（SQL 执行、Schema 读取）由后端代理执行。AI 通过 Action 请求能力，后端返回结果。

## 7. 计划即一等工件

复杂工作记录在执行计划中，附带进度和决策日志，提交到仓库。活跃计划、已完成计划和技术债务都进行版本控制并集中存放。

## 8. 测试即信心

每个层都有对应的测试策略：domain 用纯单元测试；application 用桩替身；infrastructure 用 WireMock 契约测试；adapter 用集成测试（含 E2E smoke test）。测试不是装饰，是交付的前提。
